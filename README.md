### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут удалённо включать/выключать отопление в своих домах.

**Мониторинг температуры:**

- Система получает данные о температуре с датчиков, установленных в домах. Пользователи могут просматривать текущую температуру в своих домах через веб-интерфейс.

### 2. Анализ архитектуры монолитного приложения

- **Язык программирования:** Go
- **База данных:** PostgreSQL
- **Архитектура:** Монолитная, все компоненты системы (обработка запросов, бизнес-логика, работа с данными) находятся в рамках одного приложения.
- **Взаимодействие:** Синхронное, запросы обрабатываются последовательно.
- **Масштабируемость:** Ограничена, так как монолит сложно масштабировать по частям.
- **Развертывание:** Требует остановки всего приложения.

### 3. Определение доменов и границы контекстов

- Управление устройствами (изменение статуса устройства, регулировка температуры).
- Мониторинг температуры.
- Установка датчиков, сервисное обслуживание.

### **4. Проблемы монолитного решения**
- Сложно масштабировать и выводить новые функции без остановки приложения.
- Низкая отказоустойчивость: один модуль отвечает за все.

## Описание связей

### Пользователи, роли и дома
* **Пользователь (`users`) — Дом (`houses`)** `[1:N]`: один пользователь может иметь доступ к нескольким домам, но каждый дом связан только с одним пользователем.
* **Пользователь (`users`) — Роли пользователя (`user_roles`)** `[1:N]`: один пользователь может иметь много ролей.
* **Роль (`roles`) — Роли пользователя (`user_roles`)** `[1:N]`: одна роль может быть назначена разным пользователям *(через `user_roles` реализуется связь «многие ко многим» `M:N` между `users` и `roles`)*.

### Устройства, типы и модули
* **Дом (`houses`) — Устройство (`devices`)** `[1:N]`: один дом может содержать несколько устройств, и каждое устройство принадлежит только одному дому.
* **Тип устройства (`device_types`) — Устройство (`devices`)** `[1:N]`: один тип устройства может объединять много устройств, но одно устройство имеет только один тип.
* **Устройство (`devices`) — Модуль (`modules`)** `[1:N]`: одно устройство может иметь много модулей, один модуль может принадлежать только к одному устройству.

### Параметры, телеметрия и задачи
* **Устройство (`devices`) — Значение параметра устройства (`device_param_values`)** `[1:N]`: одно устройство может иметь множество значений параметров.
* **Параметр устройства (`device_params`) — Значение параметра устройства (`device_param_values`)** `[1:N]`: один параметр может использоваться во множестве значений для разных устройств.
* **Устройство (`devices`) — Телеметрия (`telemetry_data`)** `[1:N]`: одно устройство может генерировать множество записей телеметрии.
* **Устройство (`devices`) — Задача (`tasks`)** `[1:N]`: одно устройство может иметь несколько задач, одна задача создается только для одного устройства.
* **Пользователь (`users`) — Задача (`tasks`)** `[1:N]`: один пользователь может иметь много задач, одна задача закреплена только за одним пользователем.

# Задание 4. Создание и документирование API

### 1. Тип API

Будет использовано 2 типа API: REST API и AsyncAPI.
- **REST API** подходит для синхронного взаимодействия, когда клиенту (микросервису или пользователю) нужен немедленный ответ на запрос. В данной задаче это применимо к взаимодействиям пользователя - нужен немедленный ответ. 
- **AsyncAPI** подходит для асинхронного взаимодействия, когда клиенту не нужно ждать ответа немедленно. В данной задаче этот вид взаимодействия будет использован для плановой постановки и выполнения задач устройствам.
